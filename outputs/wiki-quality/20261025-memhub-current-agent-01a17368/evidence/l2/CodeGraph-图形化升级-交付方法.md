## 工作场景
适用于 CodeGraph 平台级图形化能力迭代项目，特别是需交付多类型代码关系视图（如调用、依赖、影响范围等）并保障开发者体验一致性的中大型可视化功能交付。

## 适用条件
- 项目目标为增强代码静态/动态关系可视化能力  
- 需覆盖从基础调用到高阶影响分析的完整理解链路  
- 团队采用任务拆解制且要求子任务可独立验收  
- 前端交互需跨视图保持一致性  
- 需满足性能基准（首图交互 p95 ≤ 120ms）及完整测试覆盖（后端 ≥ 200 项，前端 ≥ 120 项）

## 核心 SOP
- 七类视图为能力交付基线：调用图、依赖图、影响范围图、聚类总览图、继承关系图、结构化图接口、集成验收，缺一不可。  
- 必须采用统一交互布局：“目录/搜索—关系图—源码详情”，禁止为单类视图定制独有导航流。  
- 默认仅加载局部关系图，所有展开（上下游/下钻）均需显式触发，不得默认全量渲染。  
- 首个子任务必须为“结构化图接口”，它是所有视图的数据与协议底座。  
- UI 布局优化执行原则&#58; ① 优先压缩非核心 UI 区域（页头/工具栏），保障画布主视区完整性；② 对可变长内容（如分析报告、关系列表）实施容器级滚动隔离，防止相互挤压。  
- 搜索交互 SOP&#58; ① 路径输入框必须标注‘可选，留空搜索整个仓库’并提供示例（如 ‘./src/main/java’）；② ‘加载更多’仅用于分页查看已检索结果，绝不触发新检索；③ 当提示‘当前仅扫描了部分索引’时，用户必须主动点击‘继续查找’，该路径需在界面或帮助文档中显式提示。  
- 模糊搜索前端机制 SOP&#58; 必须支持‘正在搜索’状态显示、请求取消与关键词即时接续、时间预算超时提示（‘检索尚未完成’），且仅当检索完全结束才可展示‘无结果’。  
- 数据库索引根本路径&#58; 必须构建名称精确匹配与前缀匹配双索引，并将目录范围条件直接下推至数据库查询层，避免全量扫描后过滤。  
- 搜索验收黄金标准&#58; 用户输入 'SvcClaim' 后单次点击搜索，首屏必须呈现 SvcClaim 类实体，并支持直接打开其关系图与源码；同时必须覆盖无结果、大小写敏感性、同名类歧义、连续换词响应性、大仓库耗时等边界场景。

## 判断逻辑
七类视图划分源于代码理解四阶演进：基础连接（调用/依赖）→ 变更影响（影响范围）→ 架构抽象（聚类/继承）→ 工程闭环（接口+验收）。统一布局确保用户在任意视图中都能以相同心智模型操作，避免认知切换损耗。性能基准（p95 ≤ 120ms）和测试覆盖要求是保障生产可用性的必要条件，而非可选优化。UI 布局原则源自桌面端主流分辨率（1920×1080）下的真实可用性验证：压缩页头与工具栏后，画布可视高度提升 32%；滚动隔离使 300 行分析报告不再挤失关系列表。搜索 SOP 设计基于开发者心智模型：精确匹配项（如 SvcClaim）必须绝对优先于派生项（如 SvcClaimMapper），这是快速定位核心类的刚需；而‘继续查找’按钮的显式设计，是为了打破‘部分索引’提示带来的操作歧义——它不是自动流程，而是明确的用户确认动作。

## 禁忌与反模式
- 不可在结构化图接口未就绪前启动任一视图的画布或渲染开发：将导致数据契约缺失，引发全量返工。  
- 不可跳过“影响范围图”单独开发“调用图”：影响分析是调用关系的自然延伸，缺失则能力断层。  
- 不得在规划建模完成前进入编码阶段：模型是交互逻辑与数据 schema 的唯一源头。  
- 不得忽略 SDK 接口继承与星号再导出的技术约束：该限制已在验收中明确提示，必须在设计与实现阶段严格遵守。  
- 不得假设动态调用可 100% 捕获：当前存在遗漏风险，必须在文档中标注“静态分析为主，动态调用需人工补充”；替代做法：在影响范围图中添加“动态调用覆盖率”状态标签。  
- 不得对大仓库聚合结果不做分页：当节点数 > 200 时，必须启用服务端分页，否则前端卡顿或崩溃；替代做法：聚合接口强制支持 limit/offset 参数，并在前端自动检测并启用分页控件。  
- ❌ 在搜索框不提供示例或用途说明文本 → 导致用户输入无效路径、放弃使用；替代做法：固定位置嵌入灰色示例文字（如 './src/main/java'）及小号说明文本。  
- ❌ 将‘加载更多’按钮语义与‘继续查找’混淆 → 引发用户误操作与状态混乱；替代做法：前者禁用 hover/active 状态变化，后者必须带 icon + 显著动效。  
- ❌ 全量扫描后过滤目录范围 → 性能灾难，大仓库不可用；替代做法：目录范围必须作为 WHERE 条件下推至 DB 查询层。
